# 服装 ERP 全模块设计方案（当前实现基线）

> 文档日期：2026-11-07
>
> 文档性质：**As-built 基线与后续建设边界**，不是待开发功能清单，也不代表生产验收结论。
>
> 适用系统：Django 5.2 + Django REST Framework 后端、微信小程序 TypeScript 前端。
>
> 核对依据：`backend/apps/*` 的模型、服务、视图和路由，`frontend/app.json`、页面与导航，以及隔离测试、契约检查、覆盖率和 UI 门禁脚本。功能是否完成仍应以对应版本回归结果和现场验收为准。

## 一、基线结论

系统已经从单一“扫菲计件”扩展为报价、订单、BOM、采购库存、裁床菲票、扫菲、工资成本、出货应收的一体化业务链，并补充轻量返工、轻量外发、订单损益、AI 问报和批量代登记。

当前实现可以概括为：

```text
基础资料 / 报价
      ↓
销售订单（颜色 × 尺码、单价、交期）
      ↓
款式 BOM（启用版本）→ 采购需求汇总 → 采购单
      ↓
采购收货（合格 / 待检 / 不合格）→ 入库批次 → 领料 / 退料
      ↓
裁床床次 → 分扎菲票 → 蓝牙标签打印 → 扫菲 / 批量代登记
      ↓
登记记录（工价快照）→ 工资结算
      ↓                 ↘
出货审核 → 应收 / 收款    订单材料、人工成本重算 → 订单损益
```

以下是**不能由上述链路推导出的能力**：系统尚无独立 APS/生产计划实体，无完整四段检验/AQL 体系，无完整委外三账与应付集成，无通用盘点/调拨/多仓库存套件，也无云打印平台实连。轻量模块不得按完整行业套件宣传。

## 二、总体架构与业务边界

### 2.1 应用划分

| 层次 | 当前应用 | 主要职责 |
|---|---|---|
| 账号与组织 | `accounts` | 用户、公司、公司成员、岗位权限、加入/切换公司、注销 |
| 核心与运维 | `core`、`ops` | 公司上下文、权限兼容、软删基类、上传、客户端日志、设置、通知、操作日志 |
| 产品与工艺 | `catalog`、`tech` | 客户、款式、颜色尺码、工序、工艺资料、菲票、物料、BOM |
| 订单与采购 | `quotation`、`orders`、`warehouse` | 报价、销售订单、供应商、采购、收货、库存批次、领退料 |
| 生产执行 | `production`、`records`、`quality`、`subcontract` | 裁床、菲票生成、进度、扫菲、批量登记、轻量返工、轻量外发 |
| 交付与资金 | `shipment`、`finance` | 出货、未交矩阵、应收、单笔/批量收款、撤销核销 |
| 薪酬与成本 | `salary`、`cost` | 四类工资、工资条/结算、订单成本、订单损益、工资对账 |
| 展示与追溯 | `kanban`、`trace`、`ai_report` | 看板、菲票追溯、自然语言问报 |

### 2.2 九大业务域现状

| 业务域 | 已实现基线 | 当前边界 |
|---|---|---|
| 订单管理 | 客户、款号、颜色尺码矩阵、行单价、交期、状态、进度、操作审计；报价可进入订单链 | 不是完整 CRM；订单变更仍须遵守下游单据约束 |
| 生产计划 | 床次关联订单、工序配置、裁货数、分扎、锁定、裁完标记、进度 | 无独立计划单、排产日历、产能平衡或 APS 优化 |
| 生产管理 | 菲票生成/查看/打印、扫码解析、当前工序推导、超量拦截、撤销、批量登记/批量撤销 | 摄像头和真实标签出纸不能由 API/UI 自动化替代验收 |
| 质量管理 | 菲票追溯、按票/工序建立返工，接收、完成、删除、筛选和 XLSX 导出 | 仅 `rework → received → done` 轻量返工；非来料/巡检/成品/出货四段检验，无 AQL、缺陷树和完整处置流 |
| 外发管理 | 外发单位、款色码、发出数、单价、分批退回、结算和导出 | 仅 `sent → partial → returned → settled`；无委外发料/回收/结存三账、应付单及订单成本自动联动 |
| 技术/BOM | 物料档案、单位换算、损耗、安全库存、款式 BOM 版本、唯一启用版本、毛需求 | BOM 服务于需求与库存业务，不等同完整 PLM/工艺变更管理 |
| 采购与仓储 | 供应商、采购单、需求汇总、暂收/IQC 分拆、入库批次、领料确认、退料、超领标记、库存估值 | 无完整多仓、库位、盘点、调拨和通用出入库单体系；面料超领不是硬性禁发 |
| 出货与财务 | 出货草稿/审核/作废、未交矩阵、自动应收、收款、撤销上次收款、客户 FIFO 批量收款 | 应收不是完整总账；无广泛应付/会计凭证集成；出货作废不自动撤应收 |
| 薪酬与成本 | 固定、整件、工序计件、计件提成四类工资；结算、工资条；材料/人工成本、间接费用、订单损益、工资对账 | 外发费字段未接入自动重算；固定工资与提成差异不会自动分摊到订单人工成本 |

## 三、多公司、认证与权限

### 3.1 公司和成员模型

- `User` 是登录身份，`Company` 是租户，`UserCompany` 是用户在某公司的成员关系；同一用户可加入多家公司。
- 岗位 `Post` 属于公司，权限挂在成员关系所引用的岗位上，而不是全局用户上。
- 成员状态必须有效。非成员、已删除成员或已停用公司不能借请求头进入业务接口。
- 同一成员在每家公司的工资方式、班组、岗位和状态分别维护。

### 3.2 请求上下文

除公开登录、本人资料、公司列表/创建/申请等明确登记的账号级接口外，公司接口统一经过 `CompanyContextMixin`：

1. JWT 认证通过后，优先读取 `X-Company-Id` 请求头；其次读取 `company_id` 查询参数。
2. 以“当前用户 + 请求公司 + ACTIVE 成员状态”查找成员关系。
3. 无有效关系按 404 拒绝，避免借接口探测他厂资源；匿名请求由认证层以 401/403 拒绝。
4. 查询集按当前公司过滤；子对象还须通过父对象公司链过滤，不能只凭全局主键访问。
5. 前端隐藏按钮不是安全边界，后端权限点与租户过滤才是最终控制。

全路由矩阵会自动发现公司接口，检查匿名访问、伪造他公司上下文、无权限成员写入和权限字典登记；真实对象矩阵另行检查跨公司读写。新增接口必须进入矩阵，不能只在页面上做隐藏。

### 3.3 权限模型

当前权限键采用 `<module>.<action>`，并保留旧粗粒度键到细分键的兼容展开：

| 权限组 | 典型能力 |
|---|---|
| `styles.*` | 款式/客户资料、上价改价、工艺资料 |
| `production.*`、`orders.*` | 床次、订单维护、状态与进度 |
| `records.create`、`records.revoke`、`scan.assist` | 本人登记、撤销、代他人登记 |
| `working.*`、`salary.*`、`employees.*` | 工作中、本人/管理薪酬、成员管理 |
| `warehouse.*`、`tech.*` | 采购库存、物料和 BOM |
| `quotation.*`、`cost.*`、`finance.*`、`shipment.*` | 报价、成本、应收、出货 |
| `quality.view/manage`、`outsource.view/manage` | 轻量返工和轻量外发 |
| `print.*`、`trace.*`、`kanban.*` | 菲票打印、追溯、看板 |
| `company.*`、`settings.*`、`logs.*` | 公司、设置、通知和日志 |

管理员或 `'*'` 具有全量权限。新增细分权限时必须同时登记权限字典并复核兼容展开。工价隐藏还需服务端控制：工序设置隐藏工价时，仅管理员、具备上价/改价或薪酬查询权限者可见，不能仅靠 WXML 不显示。

## 四、核心业务链与关键口径

### 4.1 基础资料、报价和订单

1. 先维护客户、款式、颜色、尺码、工序和默认工价；款式可带图片、工艺媒体和工序模板。
2. 报价单维护款色码、数量与报价；转订单后仍需核对订单明细价格。
3. 订单明细以 `(order, color, size)` 为核心，数量为正，单价允许为空表示未定价；`0` 是合法赠价，但出货自动应收仍有金额约束。
4. 订单状态为 `producing / done / cancelled`。状态流转不替代实际生产、出货和收款。
5. 订单进度、操作日志和菲票进度共用明确的业务对象，不以页面临时汇总作为账目。

### 4.2 BOM、采购、收货与领退料

1. 物料包含采购/库存单位、换算、默认损耗和安全库存；BOM 按款式版本管理，同一款式只有一个启用版本。
2. 采购需求按订单用量和 BOM 毛需求汇总。需求汇总不是自动审批或自动下单。
3. 采购收货将数量区分为合格、待检和不合格；合格数量进入可库存流程，待检/不合格不能被当作正常可用库存。
4. 入库形成批次，库存估值按实际业务记录计算；领料确认关联生产对象，退料冲回对应业务。
5. 领料可标记配额内或超领。面料多领用于生产弹性，记录超领标记并允许退补，不按成品出货的负库存规则硬拦。

### 4.3 裁床、菲票和打印

1. 床次可关联订单，记录款色码、裁货数和工序配置；分扎形成唯一菲票。
2. 菲票唯一性包含公司、床次和扎号；打印记录以 `print_key` 防重复。
3. `is_locked=True` 禁止继续登记；`is_cut_done` 只是裁剪完成状态，**不阻止后续车缝、尾部等工序扫码**。
4. 当前打印实现为微信端蓝牙直连 TSPL 标签，含标签预览、对位参数、打印历史和本地重试队列。
5. 路由名 `cloud-printer` 不代表已接云平台；设置页“云打印”仍为“即将支持”。不得把蓝牙连接成功、预览成功或打印历史成功等同于物理出纸验收。

### 4.4 扫菲和登记

1. 扫码后按公司解析菲票，选择允许工序；工序集优先取床次订单工序，未配置时回退款式工序，两者皆空才保持不设限。
2. 必过工序按顺序检查，前道累计登记不足扎数时拦截后道；允许跳序的工序不参与该阻断。
3. 工价优先级：**床次工序价 > 款式工序价 > 工序默认价**。登记时保存价格快照，后续改价不回写历史。
4. 0 元工序不能直接报工，避免形成无工资流水；如确需非计件质检，应使用相应管理流程而非制造 0 元登记。
5. 同扎同工序所有员工累计数量不得超过扎数；同票同工序同人的再次登记累加数量并沿用首次价格快照。
6. 床次锁定、员工状态、工序集和数量均在服务端校验；代登记要求 `scan.assist` 且目标员工是本公司在职成员。
7. 批量代登记用于“一名员工 × 一床次 × 一工序 × 多扎数量”，逐行返回结果，部分成功不能被当作整批成功。
8. 登记撤销、批量撤销和当月限制由设置及权限共同控制；撤销必须保留审计信息。

### 4.5 轻量返工和轻量外发

- 返工记录关联菲票和工序，创建后为 `rework`，接收后为 `received`，完成后为 `done`。它用于返工任务跟踪，不自动形成完整质量判定、缺陷成本或四段检验档案。
- 外发以 `send_qty × unit_price` 计算金额，分批退货推动 `sent / partial / returned`，再进入 `settled`。
- 外发金额**当前不自动生成应付，也不自动写入订单外发成本**。`OrderCost.outsourcing_cost` 虽存在，但当前重算服务没有写入来源，不能将其零值解释为“没有外发费”。

### 4.6 工资与结算

每位成员四选一，互斥：

| 工资方式 | 当前计算口径 |
|---|---|
| 固定工资 | 日薪 × 期间有登记的去重天数，或月薪 × 期间覆盖月数；非整月按代码口径计月 |
| 整件计件 | 本人参与且达到完成条件的菲票，按参与人数均摊件数，再乘整件单价 |
| 工序计件 | 未结算登记的 `Σ qty × price` |
| 计件提成 | 本组未结算计件总额 × 提成比例；未分组时无组基数，提成为 0 |

- 三类计件基数遵守未结算记录防重复规则；非工序计件通过已结快照扣减避免跨期重复发薪。
- 结算单保存工资明细快照；工资条与员工明细使用同一计算模块，不能另写一套公式。
- 工资计算、订单人工成本和财务付款不是同一概念。固定工资、提成等差额通过工资对账展示，不自动摊入订单成本。

### 4.7 出货、应收和收款

1. 出货先建草稿，审核时锁定出货单和订单，检查明细、订单未交量、成品完工结存与价格。
2. 未交量真口径：`订单色码数量 − 已审核且未作废出货明细数量`；草稿和作废单不计。
3. 系统没有独立成品入库单，“完工结存”由关联订单床次的有效扫菲登记按菲票色码聚合。出货超过该口径时硬拦。
4. 缺价必须回订单补价。审核金额按出货数量 × 订单行价计算，并自动创建应收；全部交清为 `confirmed`，否则为 `partial`。
5. `shipped / signed` 是模型保留状态，当前审核服务不会产生这两个状态，操作说明不得把它们写成必经步骤。
6. 出货作废会恢复未交量，但**不自动撤销应收**；已收款的还须先撤销核销，再到应收模块处理。
7. 应收支持逐笔收款、撤销上次收款和作废；客户批量收款按 FIFO 核销，必须核对实际分配明细。

### 4.8 成本、损益、看板和 AI 问报

- 订单材料成本来自领退料，人工成本来自登记工价快照，可维护间接费用并单批重算。
- 订单损益页用于查看收入、成本与差异，但解释数字时必须同时考虑外发费未接入、工资分摊边界和成品库存口径。
- 看板提供产量、员工、床次等经营视图；报表与 XLSX 导出以当前筛选条件为准，不等于财务法定报表。
- 首页中央“AI 问报”是独立入口。问报只能使用当前公司、当前用户有权访问的数据，不应因自然语言入口绕过公司上下文和权限。
- 普通员工首页模块远少于管理员；不能承诺任意名为“财务”“仓库”或“车间”的用户天然看到全部管理页面，必须配置岗位权限。

## 五、数据一致性与审计基线

- 业务实体继承软删基类，列表默认排除已删除数据；关键关联按业务需要保留引用。
- 唯一约束普遍带 `is_deleted=False` 条件，单据号生成须考虑软删段和并发重试。
- 出货审核、登记数量封顶、结算和收款等关键动作使用事务与行锁，避免静默超量或重复核销。
- 工价、工资明细、收款分配等需要历史口径的数据保存快照或明细，不依赖当前主数据倒推历史。
- 操作日志覆盖改价、协助登记、修改裁货数、修改工序、撤销登记及其他敏感操作；业务单状态变化也应保留操作者/时间。
- 任何“导出成功”“记录成功”“打印任务成功”都不等同于对方已收货、银行已到账或打印机已出纸。

## 六、尚未实现或需要专项验收的事项

| 项目 | 当前结论 | 后续建设/验收要求 |
|---|---|---|
| 生产计划与 APS | 未实现独立计划、排程、产能优化 | 先明确计划对象、冻结区、产能日历和订单变更影响，不借用床次冒充 APS |
| 完整质量管理 | 未实现四段检验、AQL、缺陷分类和完整处置 | 设计检验单、抽样、缺陷、判定、处置与返工/成本联动 |
| 完整委外管理 | 轻量外发已可用，三账、应付、订单成本未接通 | 补齐发料、退料、收货、对账、应付和成本来源后再调整口径 |
| 完整仓储 | 当前为采购库存和领退料轻量闭环 | 多仓/库位/盘点/调拨须独立建模并设计期初与结转 |
| 财务会计 | 已有应收，不是总账/应付/凭证系统 | 明确发票、付款、费用、凭证和期初余额边界 |
| 云打印 | 未连接云打印平台 | 完成平台鉴权、任务状态、重试、离线和真实出纸验收后才可改为已支持 |
| 真机扫码 | 静态检查与 automator 不能验证摄像头和复杂现场码 | 覆盖微信目标版本、光线、污损码、连续扫码、权限拒绝和弱网 |
| 蓝牙打印 | 代码支持 TSPL 蓝牙流程，物理效果未由本文验证 | 逐打印机验证连接、浓度、尺寸、偏移、重打、断连和实际出纸 |

## 七、测试、契约和发布门禁

### 7.1 隔离原则

- 全功能入口由 Django 创建测试数据库，并拒绝非测试库及预置真实公司 ID 86 的库。
- 不得直接对开发库、共享库或生产库执行历史 shell 测试脚本，更不得以真实公司数据做回归。
