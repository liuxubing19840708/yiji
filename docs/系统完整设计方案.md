## 一、系统定位与全景

「扫菲」是一套面向中小服装厂的**菲票扫码计件 SaaS**，已从纯计件工资工具扩展为覆盖「订单 → BOM/定额 → 采购/库存 → 裁货/扫菲 → 薪酬 → 出货 → 应收 → 成本」的轻量 ERP。核心域（存量已上线）是菲票扫码与薪酬结算；P1（成本定额 BOM）与 P2（采购/报价/出货/应收）已于 2026-10-24 交付后端并进入前后端联调；P3/P4 为规划中。

### 模块地图

```
┌─ 存量扫码域（已上线运行）──────────────────────────────┐
│ accounts 用户/公司/岗位   catalog 款式/工序/客户/菲票   │
│ production 床次/编菲      records 扫菲登记             │
│ salary 薪酬结算           kanban_template 看板配置      │
│ ops 设置/通知/审计日志     warehouse 轻量仓库+质量追溯(P1前)│
├─ P1 成本定额 BOM（2026-10-24 后端交付）────────────────┤
│ tech 物料主档/版式BOM     cost 订单成本（重算式+stale钩子）│
├─ P2 采购·应收·报价·出货（2026-10-24 后端交付）─────────┤
│ warehouse 扩展：供应商/采购/暂收IQC/领料/期初库存       │
│ quotation 报价           shipment 出货（三道审核校验）   │

├─ 支撑域 ─────────────────────────────────────────────┤
│ core 软删基类/公司上下文/契约门禁                        │
└──────────────────────────────────────────────────────┘
规划中：P3 计划/委外/质检/盘点，P4 精益/吊挂EDI（见 §八）
```

## 二、技术架构

- **后端**：Django 5.2 + DRF，JWT（`rest_framework_simplejwt`）认证，单数据库（开发 SQLite，生产 PostgreSQL，见 §七）。
- **前端**：微信小程序原生 TS（非 uni-app/Taro），页面分两侧——工人侧 `pages/`（宫格/扫码/工序/通知/我的），管理侧 `packages/admin/*`（47 个页面包）+ `packages/salary/*`（6 个）；API 层统一在 `services/*.ts`（19 个文件），经 `utils/request.ts` 注入 JWT 与公司头。
- **多租户**：`accounts.Company` 为租户边界，所有业务模型 FK 到 Company；请求经 `apps/core/mixins.py` 从 **`X-Company-Id` 请求头**（兼容 `company_id` 参数）解析公司上下文，缺失即 400；查询集一律按公司过滤，跨公司访问不可达（契约抽测已验证 401/隔离行为）。
- **软删除惯例**：`core.BaseModel`（`is_deleted` + `ActiveManager` 默认过滤）；全项目唯一约束一律带 `condition=Q(is_deleted=False)`，防软删行占用业务键（项目早期教训，订单域迁移中已系统性补齐）。

```
微信小程序 ──HTTPS/JWT──▶ Nginx ──▶ Django(DRF) ──▶ PostgreSQL
                              │
                              └──▶ 文件/媒体（款式图、视频上传）
部署细节、安全加固、备份与发布 Runbook：见 docs/生产部署设计方案.md（一句话结论：
单机 Docker 化部署 + Nginx 反代 + PG 独立数据盘 + 每日备份脚本，上机步骤以其 §10 Runbook 为准）
```

## 三、各模块设计

后端共 **15 个 app**、**153 条 API 路由**。以下按域分节；每节列职责/核心模型/关键端点/最重要的业务规则。

### 3.1 accounts — 用户与租户

- 模型：`User`（手机号登录、微信 openid 关联）、`Company`、`Post`（岗位，含 `permissions` JSON 与 `is_admin`）、`UserCompany`（用户↔公司多对多带岗位）、`SMSCode`。
- 关键端点：微信/手机号登录、公司切换、成员与岗位 CRUD（urls.py 26 条路径）。
- 规则：①一个用户可属多公司，每次请求绑定单公司上下文；②权限判定只认岗位，不认用户个体（见 §四）。

### 3.2 catalog — 主数据

- 模型：`CustomerGroup`/`Customer`、`Process`（工序+工价）、`Style`（款式，支持多图 9 张/视频）、`ProcessTemplate`/`StyleProcess`（工序模板挂款）、`Ticket`（菲票=扎）、`TicketPrintLog`（打印计数）。
- 关键端点：款式/工序/客户 CRUD、`/catalog/tickets/lookup`（手输码兜底查票）、打印上报。
- 规则：①工价变动不回溯已结算登记（薪酬快照隔离，见 3.7）；②款式多图经 mediaUrl 下发；③唯一约束均带软删条件。

### 3.3 production — 床次生产

- 模型：`Production`（床次=一次裁货，挂多张菲票；`source_order_no` 手填、`plan_qty` 计划数与实裁分账）、`ProductionProcess`（床次工序）。
- 关键端点：建床/编菲、床次列表详情、锁定/解锁、裁完标记。
- 规则：①**锁定后禁止扫菲登记**（防错登/已结款单），需管理员权限；②「裁完」仅状态标记（2026-10-18 拍板），不拦后道工序与加扎；③床次是质量追溯与领料的血缘锚点（一扎不跨批）。

### 3.4 records — 扫菲登记

- 模型：`Record`（员工×菲票×工序×件数）。
- 关键端点：扫码登记、撤销、本人登记查询、协助扫菲。
- 规则：①**同票同工序同员工唯一**（防重复登记）；②协助登记 `operator` 记实际操作人；③被结算锁定后不可改（快照隔离）；④登记/撤销触发成本 stale 埋点②（见 3.13）。

### 3.5 salary — 薪酬结算

- 模型：`Settlement`（结算单=期间登记金额快照）、`SalaryAdjust`（人工正负调整）、`SettleApply`（员工申请，状态机 待审核→待发放→已发放）。
- 关键端点：结算/撤销结算、工资配置、调整、申请审核发放、订单薪酬/完成汇总视图（12 条路径）。
- 规则：①结算即锁定登记，之后改价不影响已发工资；②撤销结算单为高危权限点（`salary.settle_revoke`）；③计件口径与 cost 劳务成本同源（whole 类按票面均摊、不读 Record.price）。

### 3.6 kanban_template — 看板配置

- 模型：`KanbanTemplate`（公司维度多套，一套默认）、`KanbanColumn`（列+绑定规则）。
- 关键端点：模板/列 CRUD、列驱动渲染数据、看板维度查看（`dashboard/dim`）。
- 规则：列配置驱动前端渲染，新增看板能力不改业务表。

### 3.7 ops — 运营支撑

- 模型：`CompanySetting`（KV，约 13 项开关）、`Notification`（站内通知，交期通知带去重）、`AuditLog`（操作日志）。
- 规则：开关类行为（如结算未结 0 拦截开关）经 Setting 读取，避免硬编码。

### 3.8 warehouse — 仓库 + 追溯 + P2 采购

存量部分（轻量仓库+质量追溯，设计见 `docs/quality-traceability-design.md`）：
- 模型：`Lot`（面料批次，批次号沿用供应商/染厂原始编号手填）、`ProductionLotLink`（床次×批次×用量血缘）、`MaterialIssue`/`IssueItem`（按床领料）、`Receipt`（退款/回收）。
- 规则：①追溯锚点=批次，血缘=床次级，领料确认钩子自动写血缘；②仓库只记流水不记结存；③**超领零硬拦**——多领是生产弹性（可退可补），落 `over` 标记并出差异报表（`issue-divergence` 前端页）。

P2 采购扩展（2026-10-24）：
- 模型：`Supplier`、`PurchaseOrder`/`PurchaseItem`（含 `price_unit` 价链）、`StockIn`/`StockInItem`、`Receipt` 复用为到料暂收（IQC 行级拆量）。
- 关键端点：供应商 CRUD、暂收 `confirm`（合格量自动采购入库、P1 价链带价）、`demand-summary` 采购需求汇总、`opening-stock/import` 期初 Excel 导入（all-or-nothing）。
- 规则：①被引用的档案（供应商/物料）软删拒删或 PROTECT；②暂收确认是库存入账的唯一入口（IQC 合格量口径）。

### 3.9 tech — 物料与 BOM（P1）

- 模型：`Material`（物料主档，主/副单位+克重/幅宽换算参数）、`Bom`/`BomItem`（版式 BOM，版本化）。
- 关键端点：物料/BOM CRUD + 导入（9 条路径）。
- 规则：①**BOM 版本唯一 active**（同款式同时仅一个生效版本）；②**单位黑洞防线**：BomItem.unit=主单位快照，用量一律折算主单位；③物料声明副单位（unit_alt）时克重/幅宽必填，缺失接口层拦截；④FK 一律 PROTECT。

### 3.10 cost — 订单成本（P1）

- 模型：`OrderCost`（每订单一行的重算式汇总表，非流水；`is_stale` 标记失效）。
- 口径（取数链三路核对定稿）：`material_cost`=Σ确认领料行×lot.unit_cost（退料冲减，缺价行不计并计 missing_price_cnt）；`labor_cost`=process 类 ΣRecord.qty×price + whole 类按票面均摊额（与 wage.py 同源）；`outsourcing_cost`=0（P3 接入后自动纳入）；`overhead_cost`=手工录入；`revenue`=ΣOrderItem 理论收入（与实收差异属预期）。
- 关键端点：成本行查询、`recompute` 重算、批量重算、`overhead` 制费录入、工资对账单（5 条路径）。
- 规则：**4 个同步 stale 埋点**（事务内、幂等）——①领料/退料确认（warehouse）、②菲票登记与撤销（records）、③订单明细价格修改（orders）、④制费手录改动（cost 自身）；翻 stale 后由重算收敛，前端展示「待重算」状态。

### 3.11 quotation — 报价（P2）

- 模型：`Quotation`、`QuoteMaterial`（报价估料）、`QuoteLabor`（工序工时×工价）。
- 规则：①**加工费=工价总和×倍率**，倍率区间 1.8-3.0 默认 2.3，超界仅 warning 不硬禁；②小单附加费（上机/制版）为独立 addon 金额项；③报价单耗与大货定额（tech.BomItem）两级精度互不干扰，选 BOM 行仅带出参照可改；④完工/出货回填对比为纯只读软提醒，不阻塞任何业务动作。

### 3.12 shipment — 出货（P2）

- 模型：`Shipment`/`ShipmentItem`（色码×尺码×数量）、`PackingBox`、`ShipmentPrintLog`（print_key 幂等）。
- 状态机：draft →审核→ confirmed（未交量清零）/ partial；shipped/signed 为预留态当前不可达；部分出货不自动拆单，余量在未交矩阵显示。
- 关键端点：建单（单号自动 SH）/改单/`audit`/`void`/`undelivered` 未交矩阵/装箱行/打印历史。
- 规则：**审核三道校验**（services.audit_shipment）——①未交量 Σ已出+本次 ≤ OrderItem.qty（400 硬拦）；②**成品负库存 400 硬拦**（与面料超领零拦截的口径差异在 docstring 写明：面料多领可回冲是弹性，成品超完工是物理错误）；③审核通过自动建应收（finance.create_receivable 服务入口）。

### 3.13 finance — 应收（P2）

- 模型：`Receivable`（应收账行，`amount` 与 `received_amount` 并行推进）、`ReceiptLine`（核销流水）。
- 关键端点：应收 CRUD（单号自动）、核销、作废、收款流水、`stock-valuation` 移动加权估值（7 条路径）。
- 规则：①核销在行级 `select_for_update` 事务内推进；②status 由核销/撤销重算（settled/partial/unpaid）；③**超额收款 400 硬拦**——口径差异与领料超领对照写明：多领可回冲，多收的钱是要退的资金错误；④出货审核与手工建单共用同一服务入口（单号自动/公司校验/审计）。

## 四、权限体系（2 段式）

- **第 1 段 legacy coarse key**：`styles / customers / production / working / my_salary / '*'` 6 个旧键，仅向后兼容，旧岗位行为零回归。
- **第 2 段细粒度权限点**：`'<module>.<action>'` 共 **40 个点、20 组**，定义于 `backend/apps/core/permissions.py:PERMISSION_GROUPS`；高危点（删除/撤销/结算）不获 legacy 覆盖，须显式授权或 `'*'`。
- 判定入口 `has_perm()`；`effective_perms(post)` 随岗位下发全量展开点集（legacy key 自动展开），前端无需复制展开逻辑。`is_admin` 与 `'*'` 恒有全部权限。

### 宫格显隐机制

- 管理侧宫格在 `frontend/pages/index/index.ts` 静态声明 28 个入口（当前质量追溯 `visible:false` 隐藏，改一行即恢复）；按 `effective_perms` 下发的点集过滤：无对应权限点的入口不渲染（如 `tech.material`→物料管理、`shipment.manage`→出货管理、`finance.view`→应收管理）。
- 工人侧宫格固定 2 项（我的薪酬、工作中）。
- 宫格内弹层按钮按权限点二次显隐（Plan A 二期，如床次详情的锁定/删除按钮）。

## 六、质量保障

### 测试体系

- **29 个测试套件文件**（26 个 `test_*.py` 脚本式 + 3 个 `e2e_*.py`）。门禁入口 `backend/run_coverage.sh` 收录 24 个：20 个脚本式套件（manage.py shell exec）+ 4 个 TestCase 模块（test_stats_refactor / test_kanban_link / test_bundle_progress / test_print_manage）；e2e_branches / e2e_edge / e2e_fullchain 在 INT 门禁单独跑。
- **动态建厂**：套件自建测试公司/员工/岗位，**真实厂数据零接触**（2026-10-23 起拟真数据专属测试厂，T0 曾修复 5 个旧套件的种子污染问题）。
- **全绿标准 ×2**：每个套件连跑两遍通过（暴露残留状态/顺序依赖）。
- **覆盖率门禁**：分支 ≥80%（当前实测分支 95.2% / 语句 98.2%，新代码 missing=0；残余不可达防御行已在门禁条款中修订豁免）。
- **契约门禁**：`backend/contract_check.py` 对比前端 services 全部 `http.<m>()` 调用 vs 后端路由表——当前**前端引用 169 个路径、后端 153 条路由、0 缺失**，另「后端先行」69 条路由 0 缺失（后端已交付、前端待联调的 P2 端点）。
- **前端门禁**：tsc 0 错误 + 小程序 CLI preview 编译通过。

### INT 集成门禁流程

六实施 agent（SA1-3 / SF1-3）交付后，由 INT 统一执行：全 L1 套件 ×2 → coverage → 契约 → tsc/preview → curl 抽测（多公司隔离/401）→ automator 真机 probe（probe_orders / probe_kanban3 / probe_scan2 等）→ 残留 ERROR 定性（区分产品缺陷 vs 测试厂残留）。流程与分工详见 `docs/系统重设计实施方案.md` §八自校验矩阵、`docs/端到端测试设计方案.md`（L1-L4 分层）。
