# Web 与小程序能力同步

## 目的

以 `scripts/capability-matrix.json` 作为双端能力基线，后端继续作为权限、金额、库存和业务状态的唯一真源。当前目标是 Web 与小程序业务功能完整对齐：同一模块、查询、写动作、状态流转、导出/打印和权限均须登记并验收。设备能力采用浏览器或微信原生实现，调用方式可以不同，但不能以平台差异为由删除业务能力，也不以静态检查代替运行验收。

## 新功能或接口变更流程

1. 先确认后端路由、字段、枚举、金额口径和权限点；必要时更新 `backend/contract_check.py` 及后端契约测试。
2. 在能力矩阵新增或更新稳定的能力 `id`，登记 API 和权限点。
3. 分别登记 Web 与小程序状态及实现入口。
4. 若某端暂不开发，使用 `planned` 并写明 `reason`；只有部分完成使用 `partial` 并说明缺口。
5. 原生能力在另一端提供等价实现；确实尚未完成的按 `partial` 登记，不能为了消除差异而伪造成功。`native-only`/`not-applicable` 会阻断完整对齐门禁。
6. 执行两端静态检查和各自运行测试。涉及真实写链路时，使用隔离公司和隔离数据。
7. UI、真机、并发和生产投递是否验证，应在交付结果中分别说明。

## 状态

- `supported`：实现已登记且静态检查通过，不等于 UI/E2E 已通过。
- `partial`：已有实现但范围不完整，必须写明缺口。
- `planned`：尚未实现，必须写明计划或原因。
- `native-only`：平台原生独有能力。
- `not-applicable`：明确不适用于该平台，必须写明原因。

## 自动检查

在仓库根目录执行：

```bash
node scripts/check-capability-sync.mjs
node scripts/check-capability-sync.mjs --json
# 发布前：不允许 partial/planned/原生例外，并检查全部小程序业务路由均已登记
node scripts/check-capability-sync.mjs --require-complete
```

也已接入（两端脚本默认启用 `--require-complete`）：

```bash
npm --prefix frontend run lint
npm --prefix frontend-web run build
```

检查内容：

- 能力 `id` 唯一，平台状态和原因完整。
- 权限点仍存在于后端权限注册表。
- 小程序页面四个源码文件存在，路由已在 `frontend/app.json` 注册；一个能力可用 `routes` 登记详情页、别名页和工作台子页。
- Web 入口文件存在，并能从 `App.vue` 的 Vue import 图到达；一个能力可用 `entries` 登记多个实际入口。
- `--require-complete` 要求每项双端均为 `supported`，并覆盖全部小程序业务路由和 App.vue 可达的全部 Web 视图；只有明确记录原因的非业务占位页可在 `route_exclusions` 排除。
- 标为 `supported` 的平台仍能找到登记的 API 路径字符串。

检查不覆盖：响应字段结构、按钮是否真正调用接口、权限运行行为、页面布局、微信编译、真机和端到端业务结果。API 检查是客户端源码范围检查，不证明某个具体按钮已接线。

## 发布门禁

后续 CI 应将双端静态检查设为必过项，再分别执行后端测试、Web 构建及浏览器回归、小程序开发者工具编译。声明双端支持的核心链路，应使用相同隔离业务数据分别验收；一端的测试通过不能替代另一端。
