# 扫菲系统「AI 入口」方案调研报告

> 调研日期：2026-10-22
> 调研对象：扫菲服装厂小程序管理系统（Django 后端 + 微信小程序 + Vue3 配置端）
> 目标：让厂长/管理员用自然语言获取经营数据（"这个月哪个组产量最高""欠产最多的订单是哪张"）并输出图形化报表（产量趋势、工序占比、质量帕累托等）
> 说明：本机 WebSearch/WebFetch 被拦（403）、deep-research MCP 连接失败，全部资料经 Bash curl 直连官方页面 / OpenRouter API / 360·必应搜索获得；各条目均标注验证方式。

---

## 0. 结论速览

1. **技术路线：推荐「路线① LLM Function Calling 直查业务只读 API」为骨架**，图表用预置模板渲染（吸收路线③），Text2SQL（路线②）仅作为 P2 阶段在受控视图上的补充。这是帆软 FineChatBI（Text2DSL 基于指标中心）等成熟产品共同的工程取向：**不让模型自由生成查询，只让模型在受控动作集里选**。
2. **首选模型：DeepSeek `deepseek-flash`**——官方文档确认支持 Tool Calls / JSON Output / Anthropic 格式，输入（缓存未命中）$0.15/百万 token、输出 $0.6/百万、缓存命中低至 $0.003/百万，且大部分时段半价（off-peak）。与 OpenRouter API 报价完全吻合（双重来源交叉验证）。按"每问 5k token"估算，**单次问答成本约 0.5~1 分钱，小厂月成本在几元到几十元量级**。
3. **调用位置：必须后端代理调用，小程序端不直连 LLM**。微信小程序 `wx.request` 需预配置合法域名且生产环境强制校验，LLM API 域名需逐个报备；后端代理可同时解决 API Key 保密、公司隔离、权限点校验、限频、缓存、审计六个问题。
4. **图表：P1 用 `echarts-for-weixin`（ec-canvas）在小程序渲染预置模板**。该库 7.5k star 但**最后提交停在 2024-06（已两年多未维护），510 个 open issue**——只用于渲染少数几种固定图表（折线/柱/饼/帕累托），不上复杂特性；备选方案是服务端出图或复用 Vue3 配置端看板。
5. **权限：AI 查数不新造权限体系**——在工具层强制 `company_id` 注入（复用现有公司隔离机制），新增独立权限点（如 `ai.ask`）控制入口，工具实现直接复用现有统计 API 的口径与隔离逻辑，天然不越权；所有问答落审计日志。
6. **分期**：P0 = 小程序对话入口 + 后端 `/ai/ask` + 8~10 个只读工具 + 文本/数字回复（1~2 周量级）；P1 = 图表卡片；P2 = 指标中心 + 受控 Text2SQL 覆盖长尾问法。

## 1. 行业同类产品的 AI 功能形态

### 1.1 通用 BI / ERP 厂商（AI 问数已成标配形态）

| 产品 | 形态 | 关键机制 | 来源验证 |
|---|---|---|---|
| 帆软 **FineChatBI** | 对话式 BI | **Text2DSL**：自然语言 → 可理解、可干预的指标/DSL；**先由管理员在指标中心搭好指标，用户基于指标提问**，而非直接生成 SQL | help.fanruan.com 帮助文档、百度百科、aibase 多源交叉验证 |
| 观远数据 **ChatBI** | AI+BI 一站式平台 | "ChatBI 自然语言问数 + 洞察 Agent + DataFlow + DecideX 决策智能体"的产品矩阵 | 官网 guandata.com 页面正文直接抓取验证 |
| 金蝶 **ChatBI** | 企业问数智能体 | 基于苍穹 Agent 平台 2.0 开发，"深度融合 AI 技术与企业数据" | 360 搜索摘要 + CSDN 文章（官网未直接验证，仅摘要级） |
| 用友 **YonGPT** | 企业服务大模型 | 用友 BIP 组成部分，**底层适配业界主流通用大模型**（自身不绑死一家），驱动业务智能决策 | yonyou.com 官网标题/摘要 + AIHub 报道交叉验证 |

**共同点（对本项目的启示）**：
- 全部走"**受限生成**"路线：要么映射到预置指标（FineChatBI 的 Text2DSL），要么映射到平台内 Agent 动作，**没有一家直接把用户 NL 转 SQL 裸跑生产库**；
- 都把"**管理员先定义口径**"作为前置条件——这正是小厂没有 BI 工程师时的落差所在，所以小厂版必须把"指标"内建在代码/工具层，而不是要求客户自建；
- 问数之外普遍叠加"洞察 Agent"（自动归因、异动提示），对应本系统可做的"欠产归因"。

### 1.2 服装行业垂直案例

- **虹软科技服装垂直大模型**：面向服装工业的垂直领域大模型，覆盖设计到生产环节的智能化（科技日报 2025-04-09 报道，360 搜索摘要验证，原文未抓全文）。
- **美邦服饰**：公告/访谈确认产品开发环节借用 DeepSeek 等 AI 大模型工具（搜狐/金融界 2025-05 摘要验证）。
- **MES + AI 对话助手的技术先例**：CSDN 有实践文章《MES 数据接入 AI 大模型：基于 MCP 协议实现工单、设备、质检统一查询》——把 MES 的工单/设备/质检数据通过 MCP 协议接给对话式 AI 助手做统一查询。**这与本课题（扫菲计件数据 + AI 问数）是最接近的可参照工程范式**：本质都是"把业务查询封装成受控工具/协议端点，LLM 只做路由与总结"（仅摘要验证）。

**小结**：服装 MES 行业尚无"AI 问数"的标准品，反而说明：通用 BI 的成熟模式（受限路由 + 指标中心）+ 本系统已有的统计 API，即可构成小厂可用的差异化能力，无需自研大模型。

## 2. 技术路线对比

### 2.1 三条路线

| 维度 | ① Function Calling 直查业务 API | ② LLM 生成 SQL（Text2SQL） | ③ 预置"指标+图表"卡片，LLM 只做意图路由 |
|---|---|---|---|
| 原理 | 把 8~20 个只读统计接口注册为工具，模型选工具+抽参数，后端执行 | 把表结构（DDL/注释）喂给模型，模型产出 SQL，后端执行 | LLM 只输出意图枚举值（如 `group_output_month`），前端渲染对应预置卡片 |
| 准确性 | **高**：口径固化在代码里，数字永远和看板/报表一致 | **风险最高**：口径漂移（"产量"算菲票还是算裁货床次）、聚合错、时间窗错。BIRD 基准 2026 新增的歧义交互（Interact）榜上，GPT-5(Med) 仅 8.67%、Gemini-2.5-pro 仅 28.67% 成功率——**顶级模型在歧义问题上仍远不可靠**（bird-bench.github.io 正文抓取验证） | **最高**（无生成环节），但理解不了枚举外的问法 |
| 权限/安全 | **天然继承**：工具内部就是现有 API，company 隔离、权限点直接复用 | 需额外建只读账号、表白名单、强制注入 company_id、禁止非 SELECT、超时/LIMIT 防护，工程量大且易漏 | 高（卡片本身受控） |
| 覆盖面 | 中：覆盖预注册的问法域（约 80% 厂长高频问题） | **最广**（长尾问法也能答） | 最窄 |
| 开发量 | 中（每工具 = 现有 stats 接口 + 一个 schema 描述） | 大（语义层+护栏+评测集） | 小 |
| 单次成本 | 低（system prompt 可被 DeepSeek 上下文缓存命中，缓存命中输入 $0.003/M） | 中（DDL+ few-shot 撑大 prompt；且错一次要重试，翻倍） | 最低（可低到几十 token 的分类任务） |
| 适合小厂程度 | **★ 首选** | ★☆ 仅作为 P2 补充 | ★★ 作为图表渲染层与 ① 配合 |

### 2.2 推荐组合（重要结论）

**① 为骨架 + ③ 的图表模板做渲染 + P2 有限度的 ②**：

- 厂长问"这个月哪个组产量最高"→ 模型选择工具 `group_output_rank(period=本月)` → 返回结构化数据 → 模型生成一句话结论；
- 前端拿到工具返回里的 `chart_hint`（`bar`/`line`/`pareto`）+ 数据，套预置 ECharts 模板渲染——**图表类型不交给模型自由发挥，只允许白名单枚举**；
- 长尾问法（P2）：先建"指标语义层"（指标名→受控 SQL 模板，参数化），模型只允许填参数不允许写 SQL 主体；如进一步开放 Text2SQL，则限定在**只读视图 + SELECT-only + 强制 company_id + LIMIT + EXPLAIN 预检**的沙箱内。

### 3.2 选型建议

1. **主力：DeepSeek `deepseek-flash`**。理由：① Tool Calls + JSON Output + Anthropic 格式三重官方确认（Anthropic 格式意味着若未来想复用 Claude 生态工具链成本为零）；② 价格双源交叉验证，是本次唯一完成双源验证的厂商；③ 缓存命中价 $0.003/M，**把固定的 system prompt（角色+工具说明+口径表）做成稳定前缀，缓存命中率可到 80%+，实际成本再降一个量级**；④ off-peak 覆盖全部周末与夜间，恰好匹配"厂长白天问、系统夜间跑批量分析"的混合负载。
2. **兜底/对比：智谱 GLM-5.3-Flash 或通义 qwen3.8-flash**（同价位量级），建议后端把 LLM Provider 做成可配置（Django settings 一行切换），P0 先绑定一家，P1 加故障切换。
3. **不推荐**：旗舰模型（deepseek-v4-pro / kimi-k3 / qwen3.8-max）做问数主力——问数任务不需要旗舰推理能力，旗舰价是其 4~10 倍；旗舰仅在 P2 复杂归因分析时按需路由。
4. **小程序端调用 vs 后端调用**：**必须后端调用**。理由：
   - 小程序生产环境强制校验 request 合法域名（HTTPS + ICP 备案 + 后台预配置），LLM 域名逐家报备不现实（微信官方文档域名本机不可达，此项为稳定既有知识，未本次验证）；
   - API Key 不能进小程序包（可被反编译提取）；
   - 公司隔离、权限点、限频、缓存、审计日志五件事都必须发生在后端——小程序直连等于把这五道门全部敞开。

### 3.3 成本估算（按 P0 形态）

- 每问成本构成：system prompt（角色+8~10 个工具 schema+口径说明，约 2k token，**绝大多数命中缓存，按 $0.003/M 计**）+ 用户问题与多轮上下文（~1k）+ 工具结果回传（~1k）+ 输出（~300 token，$0.6/M）。
- **单问 ≈ 0.5~1 分钱人民币；一个 100 人的厂每天 200 问，月成本 ≈ 3~6 元**。LLM 费用在小厂场景完全不构成约束，**反而要防的是滥用与限频失控**（见 §6）。

## 4. 图表渲染方案

### 4.1 微信小程序生态：echarts-for-weixin（ec-canvas）

- GitHub 实测（API 抓取）：**7,504 star、未归档、最后 push 2024-06-09（距今 2 年 4 个月无维护）、open issue 510 个**。
- 已知坑（既有知识 + issue 量佐证）：
  - 旧版基于 Canvas 2D 旧接口，需手动适配新 Canvas 节点；**Skyline 渲染模式下 ec-canvas 兼容性差**，webview 模式才稳；
  - 库内打包的 echarts.min.js 是定制裁剪版，自行换全量包需自己重打包；
  - issue 积压意味着踩坑只能自己读源码。
- **结论：可以用，但只用于"预置图表模板"场景**——固定 4~6 种图表（折线趋势/柱状排行/饼占比/帕累托），数据由后端结构化下发，前端不动态拼 option 之外的东西。这个用法把维护风险压到最低。若本系统小程序已启用 Skyline，则 P1 图表优先考虑 4.2/4.3 备选。

### 4.2 服务端出图（备选）

后端用 pyecharts / matplotlib（中文字体需内嵌）渲染 PNG，小程序 `<image>` 展示。优点：零前端兼容问题、图表复杂度不受限、可生成"日报图"直接转发微信群（对厂长传播价值高）；缺点：无交互、需图片存储与缓存。

### 4.3 Vue3 配置端出图（并行推荐）

本系统已有 frontend-admin（Vue3 看板体系已交付）。**P1 的图表能力建议先落在配置端**（浏览器环境 ECharts 全功能、无小程序坑），小程序 P0 先以"文本+数字表格+简版图"交付，验证 AI 问数使用率后再决定是否投入 ec-canvas 适配。**这也与"厂长真正看数的地方是电脑大屏还是手机"须用真机数据回答的现实一致。**

## 5. 数据安全与权限

### 5.1 不越权的四道闸（按执行顺序）

1. **入口权限点**：新增 `ai.ask` 权限点（对齐现有 Plan A 权限点体系，15 组 28 点的同族做法），无点的用户看不到 AI 入口；后端接口同样校验。
2. **公司隔离（硬约束，不进 prompt）**：所有工具实现内部强制带 `request.user.company` 过滤——**绝不把 company_id 交给模型决定**，模型只选工具与业务参数（时间范围、组名等）。这是与现有 API 层隔离机制天然一致的最大的安全优势。
3. **工具层只读**：P0 工具全部映射到现有只读统计接口（workbench/kanban/orders stats/traceability），不新增任何写路径；工具 schema 里不注册任何 mutating 工具。
4. **审计与降级**：每问落审计日志（问题、命中工具、参数、返回行数、耗时、token 消耗），复用现有审计链体系；工具执行超时（如 5s）直接返回业务侧超时提示，不把堆栈泄给模型。

P2 若开放 Text2SQL，追加：只读数据库账号（独立于业务账号）、表白名单视图、SELECT-only 语法校验 + EXPLAIN 预检、强制 LIMIT、禁注释/禁分号多语句、结果行数上限。

### 5.2 成本控制（缓存 + 限频）

- **结果缓存**：`问题归一化文本 + company + 用户角色` → 结果，TTL 5~15 分钟（产量类数据本就分钟级更新）；相似问法（"这个月哪个组产量最高" vs "本月产量最多的组"）先用一个极小的本地归一化（或直接把工具调用参数做缓存键），命中率会远高于文本相似。
- **prompt 缓存**：system prompt 固定前缀，吃 DeepSeek $0.003/M 的缓存命中价。
- **限频**：每用户 30~50 问/天 + 并发 1（Django 简单令牌桶即可）；超出给"今日额度已用完"。LLM 成本虽低，但要防的是 prompt 注入刷 token 与失控循环调用。
- **预算熔断**：公司级/全局日 token 预算，超限自动降级为"仅预置卡片（路线③），不调用 LLM"。

## 6. 推荐分期路线

### P0 —— 最小可用（预计 1~2 周，1 后端 + 1 小程序）

**形态：小程序"问数"对话页 + Django `ai` app + DeepSeek Function Calling + 8~10 个只读工具，纯文本+数字表格回复（无图表）。**

- 后端新增 `apps/ai`：`/ai/ask`（POST，问题→{answer_text, tools_used, data_tables}）；`/ai/suggest`（预置问法列表，引导厂长上手）。
- 工具清单（全部复用现有统计口径，参数即现有接口参数）：
  1. `group_output_rank`（组产量排行，日/周/月）——答"这个月哪个组产量最高"
  2. `order_shortage_top`（订单欠产排行）——答"欠产最多的订单是哪张"
  3. `worker_output_rank`（工人计件排行）
  4. `process_distribution`（工序占比）
  5. `quality_defect_pareto`（质量缺陷帕累托）
  6. `cutting_bed_progress`（裁床进度）
  7. `order_delivery_risk`（交期风险单）
  8. `workload_summary`（今日/本月全厂产量概览）
- 每个工具返回带 `chart_hint` 字段（P1 直接复用）。
- 权限点 `ai.ask`、限频、审计日志、结果缓存同上；LLM Provider 抽象成 settings 可配。
- 测试对齐现有门禁：契约测试（新增 `/ai/*` 契约）+ 工具层单测（口径与现有 stats 接口一致性对拍）+ LLM mock 单测（不真实调外网）。
- **P0 验收标准**：8 个预置问法 + 3 个变体问法回答口径与看板一致；无点的用户 401/403；单问 P95 < 5s；月 token 账单可查。

### P1 —— 图形化报表（P0 验证使用率后）

- 配置端 Vue3：AI 问答页 + 全套 ECharts 图表（全功能）；
- 小程序：ec-canvas 渲染 4~6 种预置图表（webview 模式验证通过才上）；或服务端出图支持"日报转发微信群"。
- 增加"洞察 Agent"型输出：欠产归因（哪个工序积压）、异动提示（某组今日产量异常下降）。

### P2 —— 语义层与长尾问法

- 建"指标中心"（对齐 FineChatBI 模式）：指标注册表（指标名、口径 SQL 模板、可用维度、权限范围），管理员在配置端维护；
- LLM 只做"问题→指标+参数+维度"的受控映射；如开放 Text2SQL，按 §5.1 的沙箱六闸执行；
- 引入评测集（50~100 条标注问法→期望指标）做回归，防止换模型/改 prompt 后口径漂移。

## 7. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 口径漂移（AI 答的数与看板不一致，厂长失去信任） | **高** | 路线①口径固化在工具层；工具结果与 stats 接口对拍测试；回答附"数据口径+时间戳" |
| LLM 服务不可用/限流 | 中 | Provider 可切换；失败降级为预置卡片模式 |
| prompt 注入（用户在问题里塞指令） | 中 | 工具层白名单校验参数；模型输出不落库不执行；system prompt 声明"用户输入仅为查询意图" |
| ec-canvas 停止维护 + Skyline 兼容 | 中 | 只用预置模板；配置端先行；服务端出图备选 |
|豆包等厂商价格/能力信息未验证 | 低 | 上线前在控制台核实；DeepSeek 已双源验证为主选 |
| 厂长不用（冷启动） | 中 | `/ai/suggest` 预置问法；AI 入口与看板页打通（在看板某卡片旁"问 AI"） |
