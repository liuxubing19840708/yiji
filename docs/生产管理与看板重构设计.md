# 生产管理与看板重构设计（款式 / 订单 / 编菲 / 扫菲 / 看板）

> 2026-10-20 起草。原则：**功能清晰、用户操作简便**。
> 调研基础：服装制造业通行范式（订单主轴 / 裁床执行 / 扎包菲票计件）+ 本项目
> docs/business-flow-audit.md（数据流审计）、docs/kanban-template-design.md（看板已做可配置化）、
> 竞品（衣扫）功能对齐结论。当前问题定位见 2026-10-20 会话分析：订单缺位、口径 4 处重复、
> 看板孤岛、建床动线 5+ 页面。

## 一、业界范式与本系统的对位

### 1.1 行业通行流程

```
客户订单(款号/交期/颜色尺码数量分解)
   → 面料采购入库(批次)
   → 裁床计划(拉布/床数推算) → 裁剪 → 打号分扎(每扎挂飞票/菲票)
   → 车缝流水(扫菲票计件) → 中烫/尾部 → 查整包装 → 出货
```

三个管理层次，职责分明：

| 层次 | 行业叫法 | 管什么 | 完成情况的"分母" |
|---|---|---|---|
| **订单层** | 客户订单/生产单(MO) | 交期、客户、整体完成度、交货 | 订单数量（颜色×尺码分解表） |
| **执行层** | 裁床/床次(lay) | 排产、裁剪、锁定 | 床次计划数 plan_qty |
| **计件层** | 菲票/飞票/扎(bundle) | 扫码计件、工序流转 | 扎数 qty |

### 1.2 当前系统对位情况

| 层次 | 现状 | 结论 |
|---|---|---|
| 订单层 | **缺位**：仅 Production.source_order_no 手填文本（追溯锚点用） | 需补建实体 |
| 执行层 | Production 床次 + plan_qty + 锁定/裁完 | ✅ 模型正确 |
| 计件层 | Ticket 菲票 + Record 登记（增量补登/累计封顶/单价快照） | ✅ 审计确认数据账正确，不动 |

## 二、领域模型调整

### 2.1 新增生产订单（唯一需要动数据模型的地方）

```python
class Order(BaseModel):                    # 表 order
    company    FK Company CASCADE
    order_no   CharField(32)               # UK(company, order_no, is_deleted=False)
    customer   FK Customer SET_NULL null  # 可空
    delivery_date DateField null          # 交期（交期风险灯）
    order_type CharField 自产/外发         # 对齐 Production.OrderType
    status     CharField producing/done/cancelled/delivered
    remark     CharField

class OrderItem(BaseModel):                # 表 order_item，颜色×尺码数量分解
    order      FK Order CASCADE
    color      CharField(64)
    size       CharField(32)
    qty        PositiveIntegerField
    # UK(order, color, size, is_deleted=False)
```

- `Production.order FK Order SET_NULL null` —— **可选挂单**（小厂散单允许无单开床，不强制）；
  `source_order_no` 保留为外部单号，挂单时自动带出、不挂时可手填（兼容存量）
- 订单完成度 = OrderItem.qty（分母）vs 该订单全部床次菲票的登记聚合（分子，按颜色/尺码逐格对照）
- 存量数据不回填；无单床次在订单看板外单列"未挂单床次"汇总
- DDL 需要：2 张新表 + production 加 1 列（均无存量数据风险，业务数据已清过）

### 2.2 不动的部分（明确防止过度设计）

- 款式（Style/StyleProcess）、工序（Process）、菲票（Ticket）、登记（Record）、
  薪酬三表、仓库批次血缘——**模型全部不动**。审计已确认核心链路
  数量账/四次价格快照/结算锁定正确；本设计的改动集中在"订单补位 + 触点压缩 + 看板分层"。

## 三、生产管理模块设计

### 3.1 订单管理（新页，订单成为管理主轴）

- **列表**：单号 / 客户 / 交期 / 订单总数 / 已完成 / 完成率 / 交期状态灯
  （绿=充裕、黄=7 天内、红=已过期未完成——阈值走 CompanySetting 可配）
- **详情**：颜色×尺码矩阵，每格 订单数/已裁/已登记/完成率；下方关联床次列表（点击跳床次详情）
- **新建**：单号（留空自动生成，对齐客户编号 KH 顺延的既有交互）/客户/交期/数量矩阵
  （复用编菲矩阵组件交互，历史颜色/尺码点选）
- 权限点：`orders.manage`（归入生产组，legacy_key='production'，老岗位零回归）

### 3.2 编菲 = 建床向导（触点压缩的核心）

现状 5+ 页面（款式建档→床次列表→编菲矩阵→详情页配工序→打印）改为**一个 4 步向导**：

```
第1步 选单选款   有单→从订单进入（自动带出客户/颜色尺码余量，只允许填剩余量内）
                无单→直接选款式
第2步 裁剪计划   床次号(预填+1) / 计划数 plan_qty / 面料 / 来源单号(挂单自动带出)
第3步 工序工价   默认整段带出款式工序价（现有 ProductionProcess 逻辑），可逐条改
第4步 生成扎     颜色×尺码矩阵 + 扎号规则（现状交互原样保留）→ 确认生成 → 引导打印菲票
```

- 生成成功即落到床次详情页（查看/加扎/打印），**完成闭环**
- 裁完标记：向导第 2 步「裁完自动标记」勾选（默认关）——与"裁完=人工标记"的待拍板项一致：
  裁床工知道自己何时裁完，勾选即标记，不搞系统猜测
- 床次详情页瘦身：工序配置移入向导第 3 步（存量床次在详情页仍可改）；锁床/裁完提升为
  列表页快捷开关 + 详情页保留
- 入口收敛：生产管理页顶部 tab「床次 | 订单」；从订单详情「开床」直达向导第 2 步

### 3.3 扫菲（不动，只加一个提示强化）

现状已是全系统最优触点（扫码→选工序→登记，增量补登/累计封顶已拍板），不改交互。
仅强化：扫到「该扎该工序已满扎数」时提示**当前累计/扎数**（现在只有"超限"文案），
工人可立刻判断是补登还是换扎。

## 四、看板管理设计

### 4.0 地基：口径唯一化（先于一切看板改动）

抽 `apps/production/stats.py` 聚合服务，唯一实现：

- `bed_progress(productions)` —— 床次进度（已登记/配满工序数→完工判定）
- `style_rows(...)` —— 计划表行（款×色聚合，现 plan_rows.py 收编进来）
- `order_progress(orders)` —— 订单完成度（P1 新增）
- `range_summary(...)` —— 完工/在制/已裁（range 口径）

**消费方全部改走它**：WorkbenchView、DashboardView（beds/summary/daily）、
计划表/看板模板渲染、款式页完成度、订单看板。此后改一次完成判定只动一个文件。
（kanban_template 依赖 plan_rows 的既有关系顺理成章收编，方向不变。）

### 4.1 三层看板（按受众分工，不做大而全）

| 看板 | 受众 | 内容 | 下钻 |
|---|---|---|---|
| **订单看板**（新） | 老板/跟单 | 每单完成率、交期灯、落后颜色尺码高亮、未挂单床次汇总 | 单→订单详情→床次 |
| **生产计划表**（现有改造） | 厂长 | 款×色行（现有列驱动模板），加「订单」列（挂单显示单号），支持按订单过滤 | 行→床次列表（预过滤款号） |
| **车间大屏**（现有简化） | 车间/工人 | 进行中床次进度 + 今日登记排行（砍掉与计划表重复的汇总区） | 床次→菲票列表 |

- 下钻实现：看板列驱动模板的 `extra` JSON 加 `link: production | ticket | order`
  （列绑定跳转类型，渲染端 tap → navigateTo 预过滤参数）——模板能力已支持列级配置，改动小
- 工作台（工人首页）保留「进行中床次」精简版，与 dashboard 的 beds 共用 stats 服务，口径天然一致

### 4.2 看板配置端同步

frontend-admin 列注册表加「订单」类目字段（order_no/交期/完成率等），
模板公式可用 `订单完成率` 等新字段——现有 formula/field 机制直接扩展，无需新架构。

## 五、实施分期

| 期 | 内容 | 量 | 依赖 |
|---|---|---|---|
| **P0** | 口径唯一化（stats.py 收编 4 处）+ 看板下钻（link 配置）+ 满扎提示 | ~2 人日 | 无 DDL，纯重构 |
| **P1** | Order/OrderItem 实体 + 订单管理页 + 建床向导挂单 + 订单看板 | ~3 人日 | DDL（2 新表 + 1 列） |
| **P2** | 建床向导 4 步化改造（含详情页瘦身、入口收敛） | ~2 人日 | 建议在 P1 后（向导第 1 步需要订单数据源） |
| **P3** | 车间大屏简化、工作台/dashboard beds 合并、交期临近通知（复用通知模块） | ~1 人日 | — |

P0 可立即开工且独立产生价值；P1 需用户对 DDL 拍板 + 第二节 2.1 的设计确认。

## 六、待拍板问题

1. **订单是否强制挂单？** 建议：可选（散单/翻单无单开床），订单看板单列未挂单汇总。
2. **订单数量分解粒度**：颜色×尺码矩阵（建议，与编菲粒度一致）还是仅颜色（省事但订单看板只能按色汇总）。
3. **次品/返工**是否纳入订单完成口径？当前系统无次品登记概念（行业上返工菲票常见）——
   建议二期，先按"登记量=完成量"口径。
4. **交期提醒**：交期前 N 天通知管理员（通知模块现成，P3 顺带）——要做吗？N 默认 7？
5. **外发订单**（order_type=外发）是否需要跟踪回厂入库？（与追溯二期"外发"遗留项合并考虑）
